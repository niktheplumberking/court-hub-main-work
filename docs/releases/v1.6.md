# Court Hub v1.6: reusable order confirmation emails

Status: implementation and local previews. Live activation and inbox tests are pending access to the Court Hub Resend account and production VPS. Previous release: v1.5, `8ef0b1de6406c1a0f717df967e7231a0a9c6790f`.

## Messages

- Owner: new paid order, the same eight-character reference used by the website, date in Dubai time, product photographs, quantities, unit/line prices, actual amount paid, customer contact and shipping details, and a protected admin-dashboard link. Destination defaults to the client-provided `Court.hub.ae@gmail.com`.
- Customer: personalised thank-you, confirmation/reference, item photos and quantities, paid amount, delivery details and next steps, support telephone `+971 55 883 3836` and WhatsApp. English or Arabic according to the checkout language; old sessions default to English. Replies go to the owner. No tax invoice, tax breakdown or dispatch-time promises are invented.
- Both use navy `#0A2A66`, sky blue `#8EC5FF`, the Court Hub wordmark, a 600px table layout with inline styles and a plain-text alternative. No em dashes. Product photos are restricted to Court Hub and its current Supabase storage hostname. Customer fields are HTML-escaped.
- Templates live in `lib/email/order-email.ts`, shared by local previews, sample sends and production. The template version and immutable queued message preserve stable retry bodies if a later release changes copy.

## Production integration and durability

This installation runs on one Hostinger VPS. Its durable, private filesystem outbox is outside the source/build at `/var/lib/courthub/order-emails`. It contains customer data and must remain mode 700, with files mode 600, excluded from Git and public web roots, and included in the owner's protected server backups. It is not suitable for Vercel/serverless or multiple hosts; such a move requires a shared transactional queue first. Vercel environments explicitly refuse email activation.

Only a verified paid Stripe session reaches the existing fulfillment function. After the order is recorded and stock conversion succeeds, it awaits a complete, atomically published message envelope. The owner/customer messages are separate jobs. A filesystem error fails the webhook so Stripe retries rather than acknowledging an unqueued email. The success-page fallback uses the same envelope. Concurrent callbacks use exclusive filesystem linking and do not overwrite the original recipients/body. Only orders created on or after `ORDER_EMAILS_SINCE` are queued; old orders are not backfilled. Cancelled orders are not newly queued. A later cancellation does not retract an already queued order confirmation.

Delivery runs outside checkout, with an OS-wide `flock`, once per minute. Receipts persist independently for each recipient. Successful messages are not resent on duplicate webhooks, restarts or deployments. Retryable failures use bounded exponential backoff and stable Resend idempotency keys. Uncertain sends reaching 20 hours are held for manual review, safely inside Resend's 24-hour deduplication window. Permanent provider failures are also held for review. Worker logs include counts and order IDs only, never message bodies, addresses or API credentials. Worker exit 2 means review is required. Review records are deliberately not reset automatically. Missing customer email is logged using only the order ID; owner notification can still be queued.

No database schema, customer data migration, payment API, product prices or stock rules change. No public email-sending endpoint is introduced. Test emails use fictional details, a `[TEST]` subject and a prominent no-purchase/no-charge banner. The manual sample script does not create an order, reserve stock or charge a card.

## Setup after preview and inbox checks

1. Verify `courthub.ae` or its designated sending subdomain in the correct Resend account, including SPF/DKIM. Use a verified sender such as `Court Hub <orders@courthub.ae>`; Gmail addresses are notification/reply recipients, not an authenticated Court Hub sender. Preserve existing MX/SPF records when arranging DNS.
2. Put `RESEND_API_KEY`, `ORDER_EMAIL_FROM`, `ORDER_NOTIFICATION_EMAIL`, `ORDER_EMAIL_OUTBOX_DIR`, `ORDER_EMAILS_ENABLED=false` in `/var/www/courthub/.env.local` through a protected session. Never put credentials in chat, source, URLs or shell arguments. Keep `.env.local` mode 600. Use a sending-only/domain-scoped API key when supported.
3. Build the candidate in a separate release directory with the existing protected environment. `npm run build` includes the standalone email worker. Install the private outbox directory with `install -d -m 700 /var/lib/courthub/order-emails`.
4. `node scripts/preview-order-emails.cjs` writes fictional review files under `.qa/v1.6-email-preview/`. Review owner, customer and Arabic customer files. Test with `node --env-file=.env.local scripts/send-order-email-test.cjs --to ADDRESS --run UNIQUE-NAME` (repeat `--to` for expressly approved test inboxes). Avoid overlapping manual invocations. Reuse the run name for safe retries. Verify provider **Delivered**, SPF/DKIM/DMARC alignment and actual recipient inbox appearance, including images, phone/WhatsApp links and mobile layout. API acceptance is not a delivery claim.
5. Keep the v1.5 source/environment/build backup, push the tested v1.6 branch and immutable tag, then publish the prepared build with the existing rollback procedure. Set `ORDER_EMAILS_SINCE` to the actual activation UTC time and `ORDER_EMAILS_ENABLED=true`, then restart only `courthub` with the updated environment. Do not change the cutoff during later upgrades. The recorded order timestamp, not the Stripe-session creation timestamp, controls eligibility.
6. Install a root-only cron file `/etc/cron.d/courthub-order-emails`: `* * * * * root /bin/bash /var/www/courthub/scripts/run-order-email-worker.sh >> /var/log/courthub-order-emails.log 2>&1`. Ensure `/var/lib/courthub` exists and the lock path is writable by the same app/worker account. Keep the log private and rotated. Run one manual worker invocation under the same lock and inspect receipts/counts. Monitor review/pending jobs and Resend delivery/bounce logs. Successful API acceptance records a sent receipt, not guaranteed final delivery.
7. Use a Stripe test-mode purchase with expressly approved test recipients if testing the entire live checkout is authorised and test inventory is isolated. Do not manufacture a real order or charge to test the templates. Automated local fulfillment tests cover paid/unpaid triggers without network or live stock writes.

## Checks and rollback

`npm run lint`, `node scripts/test-order-emails.cjs`, `node scripts/test-order-email-fulfillment.cjs`, existing regression scripts and `npm run build`. Native browser previews cover desktop/mobile and Arabic. Actual inbox acceptance/delivery remains separate evidence.

Disable `ORDER_EMAILS_ENABLED`, stop the email cron, restore the saved v1.5 source and `.next` build, restart only `courthub`, verify health and save PM2. Preserve the outbox and receipts during rollback, since deleting them could cause duplicate notifications when re-enabling. Do not restore old Stripe/Supabase state or decrement/reinstate stock as part of an email rollback. Never reset an uncertain receipt without checking its Resend message ID/idempotency key and delivery state first.
